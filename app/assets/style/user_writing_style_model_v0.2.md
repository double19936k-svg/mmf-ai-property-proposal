# User Writing Style Model V0.2 Candidate

版本：V0.2 Candidate  
生成日期：2026-08-24  
适用范围：物业服务方案PPT、物业技术标Word及内容底稿  
状态：`candidate_pending_human_acceptance`  
来源：User Writing Style Model V0.1 + 24项Todd人工校准答复 + S1-002人工验收反馈  
规则数：57条（强制15、默认13、条件17、禁用12）

## 0. 模型边界

V0.2 Candidate是Sprint 1的候选输出，不是已冻结的不可变个人规则。当前尚未完成Historical Gap Learning，也没有通过新项目Holdout验证V0.2的实际修改量。

生成时遵循以下优先级：

> 当前项目事实、招标/合同强制要求和合规要求 > 强制规则 > 条件规则 > 默认规则 > 样本观察与分析推断

风格规则不得覆盖项目事实、评分项、合同边界、现行标准或Todd的项目专项判断。

本轮人工验收反馈已确认CAL-13商业责任边界、C-009“运营性审查”和C-016作者权重解释；原D-010停止作为默认规则使用，由C-017承接项目条件判断。当前仍处于候选验收阶段，不代表已冻结。

## 1. 四档规则定义

- **强制（Mandatory）**：默认必须执行；只能因项目强制要求或Todd明确决策偏离，并记录原因。
- **默认（Default）**：无更强项目证据时执行；允许有理由地调整。
- **条件（Conditional）**：只在指定业态、媒介、采购角色或责任边界成立时执行。
- **禁用（Prohibited）**：用户可见稿不得使用，或必须在出稿前改写。

## 2. 强制规则（15条）

| ID | 规则 |
|---|---|
| M-001 | 方案必须从当前项目事实和客户/场景出发，不先搭方法论模型。 |
| M-002 | 生成前必须明确项目类型、建设/运营阶段、采购角色、主要使用者和强制响应项。 |
| M-003 | 章节和标题必须能够识别物业业务对象或项目任务，自创概念不得替代专业内容。 |
| M-004 | 每个核心措施块至少写清对象和动作；涉及执行时进一步写清责任、标准、记录或成果。 |
| M-005 | PPT中“应急管理”与“培训”不合并为同一保障模块。 |
| M-006 | Word技术标中KPI表、岗位表、检查表、预案和证书按当前招标评分点展开，不固定全量配置。 |
| M-007 | 任何案例都必须说明与当前项目的可比点；客户名称或图片墙不能单独作为能力证据。 |
| M-008 | 人数、价格、频次、时限、阈值、KPI、法规和效果数据必须有当前项目或可核验来源。 |
| M-009 | 未知人数、频次、阈值和责任边界集中进入澄清清单，不在每个小节重复“待确认”。 |
| M-010 | 前期介入、承接查验、客户报事/投诉、工程维修、应急上报、供应商管理和品质整改必须有流程与责任。 |
| M-011 | 品质管理必须写清标准/计划、检查、记录、整改和复核的关系。 |
| M-012 | PPT与Word技术标必须按媒介重组，不允许把Word机械缩写成PPT，或把PPT要点机械扩写成Word。 |
| M-013 | “闭环”只能用于能写清受理、处理、反馈、复核或关闭步骤的具体流程；不在总体策略和每个专业模块重复使用。 |
| M-014 | 当前项目事实、招标/合同原词、评分要求和合规边界优先于风格默认值；任何偏离必须可说明。 |
| M-015 | 输出优先解决项目问题，不追求表达创新；创新表达必须服务于业务理解。 |

## 3. 默认规则（13条）

| ID | 规则 |
|---|---|
| D-001 | 常规项目默认按“项目概况—客户/业态分析—服务设想—专业服务—保障”组织。 |
| D-002 | 对外标题默认使用“管理目标、服务保障、服务模式”等客观语句，不使用“我们的X”。 |
| D-003 | 专业目录默认使用客户服务、工程管理、环境管理、秩序/安全管理等业务标题，再根据项目删减。 |
| D-004 | 对外稿推荐使用“服务措施”作为章节或内容块用词。 |
| D-005 | 正文默认使用“具体名词 + 现场动作 + 管理结果”，优先写检查、记录、维护、巡查、验收、培训、整改和回访等工作。 |
| D-006 | PPT默认为中等至中高信息密度，每页围绕一个明确主题承载必要信息块。 |
| D-007 | PPT每页默认先给项目判断或主题，再给服务措施、流程、标准或证据。 |
| D-008 | Word技术标默认按“评分点—章节—措施—标准—证据”建立响应关系。 |
| D-009 | 产业园和商业PPT中默认主动评估并提高数字化内容权重，但数字化必须对应场景、系统能力或服务动作。 |
| D-011 | 项目理解和客户/场景分析默认放在公司介绍与通用能力展示之前。 |
| D-012 | PPT默认不展开3—6页通用公司介绍，把篇幅优先留给项目判断和服务措施。 |
| D-013 | 案例和能力证据默认靠近它所支撑的项目判断、服务措施或评分项，不单纯集中堆叠。 |
| D-014 | 口号或服务特征短句最多作为引导，后续默认用工作内容、流程、标准和案例支撑。 |

## 4. 条件规则（17条）

| ID | 规则 |
|---|---|
| C-001 | 只有重要汇报、商务证明或甲方明确要求时，PPT才保留公司介绍、客户、荣誉和业务分布。 |
| C-002 | 新建、在建或交付项目设“前期介入”和“承接查验”专章；已运营项目仅在需求涉及接管时保留。 |
| C-003 | 会务、高管区、保密和EHS只在银行、金融、总部或当前项目明确有相同需求时强化。 |
| C-004 | “大物管、城市治理、全域运营”只用于城市更新和公共空间项目，且必须迅速落到环卫、绿化、安全、设施、商户和公共空间措施。 |
| C-005 | 商业招商与经营协同的责任划分必须来自当前采购范围、甲方确认或项目资料，不得默认由物业团队承担招商经营责任。 |
| C-006 | 目前不建立FM运营方案/FM顾问方案的固定双模型；真实FM项目按采购角色重新组织语言。 |
| C-007 | 康养项目暂不调用固定分支，出现项目时按客户、健康、生活和社群场景重新分析。 |
| C-008 | “工作包”可在内部底稿作WBS管理用语；用户可见PPT/Word改为工作内容、专项工作或工作计划。 |
| C-009 | “运营性审查”可在招标原文未出现时保留，但必须紧接设计、施工、系统、使用或后期运营角度的具体审查动作。 |
| C-010 | “退出验收”只在合同或招标文件明确时使用；其他情况改为成果移交、工作交接和合同验收。 |
| C-011 | RACI、SOP、SLA、KPI等缩写只在甲方使用相同术语、内部底稿或确有专业必要时保留；对外正文默认中文化。 |
| C-012 | “顾问”只在当前采购角色确为顾问服务时用于审查、建议、培训和督导，不与治理中枢或能力转移等概念连续绑定。 |
| C-013 | “治理”只在有明确对象时使用，如供应商治理、质量治理和城市治理；不升级为所有项目的总方法。 |
| C-014 | “生命周期”只在工程设施或项目阶段确有周期含义时使用，不叠加“价值链、成果闭环”。 |
| C-015 | “接口”只在共享设备、共享区域或跨单位交界真实存在时使用；普通配合事项写责职分工。 |
| C-016 | 代表语料可以因用户估计“约70%以上本人编写”提高整体权重，但任何具体文件、段落和口号仍需区分个人策划、团队整合和公司模板。 |
| C-017 | 根据项目定位、合同范围和物业角色评估是否纳入招商与经营协同；如纳入，再按C-005明确责任边界。 |

## 5. 禁用规则（12条）

| ID | 规则 |
|---|---|
| P-001 | 禁止把“兼备环球视野与本土实力”“服务无止境”等历史企业口号进入未来个人表达体系。 |
| P-002 | 禁止用“一个治理中枢、两种模式、四个阶段”等自创上位模型代替项目工作。 |
| P-003 | 禁止使用“治理节奏”代替工作安排、阶段会议、巡场节点和汇报审签。 |
| P-004 | 禁止使用“九维运营就绪”代替人员、制度、资料、供应商、物资、培训、现场和查验准备。 |
| P-005 | 禁止用“能力转移闭环、连续价值链、统一成果闭环”代替培训辅导、管理提升、成果移交和阶段确认。 |
| P-006 | 用户可见PPT/Word禁止用“六类工作包、并行工作包”作为方案章节语言。 |
| P-007 | 禁止用“共享治理底座、差异化前台”等中台/产品架构隐喻代替共性管理与分业态标准。 |
| P-008 | 禁止用“能力成熟度、能力基线”代替团队现状、培训计划、现场表现和独立执行情况。 |
| P-009 | 禁止用“阶段门、质量门、转段逻辑”代替“本阶段完成并经甲方确认后进入下一阶段”。 |
| P-010 | 禁止用“证据治理、证据架构”代替档案、记录、台账、报告、签字和保管要求。 |
| P-011 | 禁止把“行动出口、阻塞后续工作、回写成果版本、场景验证脚本、终态”等产品研发语言直接写入物业方案。 |
| P-012 | 禁止从历史方案迁移无当前依据的人数、响应时间、频次、KPI、成本、法规和效果数据。 |

## 6. 业态与媒介快速调用

### PPT

- 突出项目判断、业态场景、核心服务措施和少量可比证据。
- 应急管理与培训分开表达。
- 数字化可作为主动策略，但必须回到具体场景与动作。
- 公司介绍只在重要汇报或商务需要时保留。

### Word技术标

- 先覆盖评分要求，再体现项目针对性，最后用人员、标准、记录、案例和证书证明。
- 表单、预案和证据的深度按评分点展开，不固定全量配置。
- 流程、职责、标准、检查、整改和复核必须具体。

### 业态分支

- **产业园**：项目业态和多客户差异、前期介入、承接查验、生产安全、设施设备、企业服务和数字化。
- **写字楼**：项目定位、客户与来访场景、客户服务、工程运行和品质体验；银行/总部分支再强化会务、高管区、保密和EHS。
- **商业**：根据项目定位、合同范围和物业角色评估是否纳入招商与经营协同；如纳入，明确甲方、招商团队与物业团队边界。
- **城市更新/公共空间**：允许使用城市治理与大物管叙事，但必须落到现场责任和专业措施。
- **FM**：暂不建立固定双模型，按真实采购角色重新组织。
- **康养**：暂不设固定分支，项目出现时重新分析。

## 7. 生成前后检查表

### 生成前

- 确认媒介、项目类型、阶段、采购角色、使用者和强制响应项。
- 分开当前项目事实、专业知识、历史参考和待澄清项。
- 识别本项目应调用的条件规则。

### 生成中

- 一级标题直接反映项目任务或业务模块。
- 每个措施块至少包含明确对象和动作。
- 抽象词后有具体责任、流程、标准、记录或成果。
- 按业态和媒介调整内容权重。

### 生成后

- 扫描P-001—P-012，清理历史口号、自创模型、产品研发语言和虚假精确。
- 检查所有案例的可比点。
- 检查所有数值、承诺、法规和公司话术的来源。
- 将未知事项集中到澄清清单，再进入人工审查。

## 8. 候选模型验收条件

V0.2 Candidate只有在以下条件满足后才可冻结：

1. Todd审查57条规则的档位和文义。
2. CAL-13、CAL-17、CAL-22的解释已由Todd确认；本轮新增M-015并将原D-010调整为C-017后，仍需完成整体验收。
3. 使用至少一个边界清晰的项目样例进行规则检查，记录与V0.1的修改差异。
4. 未将Historical Gap Learning、RAG、向量库或MVP生成器冒充为已完成能力。
